## 記事の主張（著者の報告）

1. **秘密値の読み取りガードが別の道具で突破された。** `cat`・`grep`・`sed` 等で `.env` を読むのを止めるフックが、インタープリタの1行実行で素通りした。`permissions.deny` の読み取りルールも、シェルから起動されるプログラムの読み取りまでは見ない。対策は「道具名」ではなく「コマンド中に現れる対象ファイル名」で止めること。さらに、ディスク上の既存スクリプトが中でファイルを開く場合はコマンド文字列に名前が出ず検知できない、という限界を文書に明記した。著者の結論は、本当に守りたい値はそもそも開発機に置かないこと。フックは外側の網にすぎない。
2. **保護ブランチのガードが改行1つで突破された。** トークナイザが改行を区切りではなく空白として扱ったため、1行目の別コマンドだけが判定され、2行目の force push が通った。エージェントは改行でコマンドをつなぐことが多い。テスト表を書くまで気づかなかった。
3. **直したら止めすぎた。** `bash -c`・`eval`・リモートシェル・シェルに渡すヒアドキュメントの中まで見るようにすると、コミットメッセージ、`echo` の引数、ファイルに書き出すだけのヒアドキュメントで誤検知した。対策は「実際に実行される文字列だけ」を見ることと、「止めるもの」「止めないもの」を同じテスト表にして CI で回すこと。
4. **フックは静かに通す側に壊れる。** ブランチ名の判定が呼び出し元の作業ディレクトリに依存し、リポジトリ外では空になって判定が丸ごと抜けた。エラーは出ない。
5. **レビュー役のAIが、レビュー対象のPRに操られうる。** PR の head をチェックアウトした場所でレビュー役を起動すると、そこにあるエージェント設定（フック設定、ツールサーバー定義、ルール）を読み込む。PR 作成者が設定ファイルを足せば、レビュー役の起動時に任意の処理が動きうる。著者は OWASP CICD-SEC-4（Poisoned Pipeline Execution）と LLM01（Prompt Injection）に対応づけている。6層の対策は、(a)信頼済みディレクトリの外にチェックアウト、(b)起動前に作業コピーからエージェント設定を削除、(c)プロジェクト設定とツールサーバーを無効化し読み取り専用で起動、(d)審査ルールは**ベース側**の版を使う、(e)結果から鍵らしい文字列を伏せてから投稿、(f)合格を付ける直前に PR の head が変わっていないか比較。通知は1行の状態だけにした（削るより最初から載せない方が確実）。
6. **自己点検チェックリスト**（秘密の読み取り、危険コマンド、AIレビュー）。通知先のURLやトピック名を鍵として扱う項目を含む。

## このリポジトリとの既存の対応

| 記事のテーマ | 既存の対応 | ギャップ・限界（脆弱性と断定せず、要検証） |
|---|---|---|
| 保護ブランチ | `PolicyEngine.evaluate_git_operation` とハード拒否集合は、生のシェル文字列ではなく構造化引数（対象ブランチ・操作・force）を受け取る（[policy.py](../../orchestrator/core/policy.py)）。 | 構造化入力が改行・入れ子の解析バグを避けられるのは、全ての呼び出し側が実際のコマンドから正しく引数を作る場合のみ。実行コマンドからこの引数への対応が網羅的であることは示されていない。 |
| コマンド許可リスト | `evaluate_command_id` は先頭トークンを `DEFAULT_ALLOWED_COMMANDS` と照合する。一覧には汎用インタープリタ（`python3`、`node`）と `git` を含む。 | 先頭トークンの許可は名前ベース。インタープリタは見えるファイルを何でも開けるため、防御の実体はこの判定ではなくコンテナ／worktree 境界（[runtime-isolation](../operations/runtime-isolation.md)）にある。 |
| ワーカーへの秘密流入 | `sanitize_worker_environment` が認証情報らしい環境変数を除去し許可リストで絞る（[sandbox.py](../../orchestrator/core/sandbox.py)）。 | 環境変数の除去は、マウントされた作業領域内の認証情報**ファイル**には及ばない。 |
| 独立検証・レビュー | [AGENTS](../../AGENTS.md) で Builder / Tester / Reviewer を分離。`IndependentVerifier` が結果を収集。 | 役割は宣言とフェーズであり、レビュー役のプロセスがレビュー対象の候補から設定を読み込むかどうかは、確認した文書ではカバーされていない。 |
| フック | `HookEngine` と `run_command_hook` は `cwd` を明示的に受け取る（[hooks.py](../../orchestrator/core/hooks.py)）。 | 文脈が欠けたときの fail-open / fail-closed は、確認した文書に規定がない。 |
| ネガティブテスト | [test_guardrail_negatives.py](../../tests/negative/test_guardrail_negatives.py) がある。 | 「止める」ケースごとに「止めない」ケースが対になっているかは未確認。 |

## 改修提案（未実装）

各項目は拡張先のロードマップ段階（[ガバナンスロードマップ](../architecture/governance-roadmap.ja.md)）と完了条件を示します。既存のセキュリティ境界は変えず、既存作業に追加する形です。

| ID | 提案 | 段階 | 完了条件 |
|---|---|---|---|
| R1 | **道具名ではなく対象リソースで拒否する。** コマンド許可リストと並べて、どの実行ファイルが呼ばれるかに依存しない、秘密を含むファイル／ディレクトリのパス拒否層を追加する。 | G2 | インタープリタ1行実行・コピー・エンコード・リダイレクトによる保護パスへのアクセスが、明白な読み取りコマンドと同じルールで拒否されるテストがある。 |
| R2 | **各ガードの横に残存ギャップを明記する。** ガードごとに「見えないもの」（例：既存のディスク上スクリプトによるファイルオープン）と「実際に支えているもの」（コンテナ境界、秘密をそもそもマウントしない等）を記録する。重要な秘密は作業領域に置かない方針を優先する。 | G1 | 脅威モデルと PROJECT_STATE に各ガードと既知の死角が載り、限界の記載がないガードは文書レビューで通らない。 |
| R3 | **生のコマンド文字列より構造化 argv を優先。文字列を解析する場合は改行を区切りとして扱い、実際に実行される文字列だけを検査する。** 連結コマンド、`bash -c`、`eval`、リモートシェル、シェルへのヒアドキュメントを対象にし、コミットメッセージ・echo の文字列・ファイルへ書くヒアドキュメントは除外する。 | G2 | 連結・入れ子・単なる言及の各形を含む固定テスト表が、両方向（止める／止めない）で通る。 |
| R4 | **「止める」と「止めない」を同じ CI 表に対で置く。** 穴を塞ぐ修正が誤検知を生む（またはその逆）ことを見逃さない。 | G1 / G4 | 対になる「止めない」ケースのない拒否ルール追加（または逆）は CI で失敗する。 |
| R5 | **文脈が欠けたら fail-closed。** ガードは呼び出し元の作業ディレクトリや推定したブランチ名に依存しない。空・未解決の値は拒否（または承認要求）とし、黙って通さない。判断できなかったことを監査可能な形で記録する。 | G2 | リポジトリ外や未解決の入力で各ガードを呼び、拒否と理由の記録が確認できるテストがある。 |
| R6 | **レビュー役にとって候補は「データ」であり「設定」ではない。** 信頼済みディレクトリの外にあるコピーをレビューし、起動前に エージェント設定（フック、ツールサーバー定義、ルール、指示ファイル）を取り除き、プロジェクト設定とツールサーバーを無効化し読み取り専用で起動し、審査基準はベース側の版から読み、合格記録の直前に候補の head を再比較し、レビュー出力から鍵らしい文字列を伏せる。G2 のダイジェスト束縛の考え方と [GitInject 調査](gitinject-2606.09935.ja.md) を拡張する。 | G2 / G5 | 候補がレビュー役設定を追加したり自分の審査基準を書き換えたりしてもレビューに影響せず、レビューから合格記録までの間に head が変われば合格がブロックされる。 |
| R7 | **通知とレビューコメントに載せる内容を最小化し、通知先エンドポイントを秘密として扱う。** 状態のみのメッセージにし、信頼チャネル外に自由記述のレビュー本文を出さない。伏せ字は主対策ではなく最後の網。 | G4 | 通知が許可フィールドのみを含むことを確認するテストがある。 |
| R8 | **自分のガードを定期的に攻撃する。** レッドチーム用チェックリスト（別ツールでの秘密読み取り、連結・入れ子コマンド、別ディレクトリからの呼び出し、汚染されたレビュー入力）を G4 パイロットで実施する。読み取り専用のソース監査も任意で併用。 | G4 | チェックリストを実施し、見逃しも含め結果を記録し、見逃しごとに R3/R4 型の回帰ケースを追加している。 |
